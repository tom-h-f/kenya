# Retire the v1 coordination detector

Decided 2026-10-10: v1 stops now. It was the only detector running
continuously (`analysis-enrich-1` on tf1), at 18.6% recall on the IO archive and
0 of 11 Kenya-relevant in the blind read; v2 runs daily on `cloud`. This is
C5 of `2026-09-05-v2-next-steps.md` and replaces decision 9 of
`2026-09-22-detection-readiness.md`.

Branch `chore/retire-v1`. Nothing here deploys; the checklist at the end is the
order to do that in.

## What stops

| Piece | Where | Change |

## Soft-off, no code deploy

tf1 runs `enrich.py` byte-identical to this repo's `master`, so the env vars
below act on what is deployed. tf1's `~/kenya-monitor-2027/.env` holds only the
four `R2_*` keys today, so every default is live: coordination every 6h
(first one at startup), scorecards every 24h, adjudication off.

Add to `~/kenya-monitor-2027/.env`:

```
COORD_REFRESH_HOURS=0
SCORECARD_REFRESH_HOURS=0
ADJUDICATE_REFRESH_HOURS=0
```

Then `docker compose up -d --force-recreate enrich` in `~/kenya-monitor-2027/analysis`.
`restart` is not enough: `env_file` is read when the container is created.

`0` disables each pass because `run_loop` sets its next-due time to infinity
when the hours are `<= 0`, so `time.monotonic() >= next` never holds. The values
are read at import as defaults for both `run_loop` and the `--coord-hours`,
`--scorecard-hours`, `--adjudicate-hours` flags, and compose passes only
`--loop`. No other variable matters: `COORD_RETRY_MINUTES` only applies after a
pass has run.

Confirm, in order of speed:

1. `docker exec analysis-enrich-1 env | grep -E '^(COORD|SCORECARD|ADJUDICATE)_REFRESH_HOURS='` shows `0` for all three.
2. Startup: no `coordination refreshed and persisted` or `coordination refresh failed` line after the recreate. With the old config the first one lands within the first cycle.
3. `docker top analysis-enrich-1` never shows `kma.coordination_run` or `kma.scorecard_run` among the subprocesses.
4. After one full enrich cycle (about 4h), no `scorecards refreshed` and no `scorecard refresh failed`; after 7h, still no coordination line.
5. R2: the newest object under `coordination/platform=x/kind=run_metrics/` stops advancing.

What this removes, from the tf1 logs of 2026-10-09 and 10: a coordination pass
about every 7h (373, 367, 357, 352 clusters), and a scorecard pass that fails
with rc=1 on every cycle, about every 4h. The incitement pass is also being
OOM-killed (rc=-9) once per cycle at the 2g cap; that is not touched here.

## Deploy checklist

Gate: the cloud daily has produced a `coord2/platform=x/kind=scores` run.
`monitor deep-timelines --dry-run` on pi0 prints that run's `computed_at`; it
must be under 24h old before step 1.

The gate is a precondition, not a technical dependency. pi0 promotion is
already off (`cluster promotion disabled` in the pi0 log), so removing the code
changes no behaviour there, and nothing the collector reads comes from v1 any
more. What the gate protects is not stopping the only coordination output
before any v2 output exists.

1. tf1, soft-off: add the three variables, recreate `enrich` (above). Confirm.
2. tf1, diff before sync. `~/kenya-monitor-2027` is not a git checkout. Its
   `kma` package is mid-August vintage for most modules (no `coord2`,
   `v2_daily` or `leads_*`; `enrich.py` is byte-identical to master), and its
   `analysis/compose.yaml` differs from the repo: `mem_limit: 2g` and a
   2026-09-29 OOM note, with `compose.yaml.bak*` beside it. Run `diff -r` of the
   tree against this branch's `analysis/` and read all of it. Never rsync a
   checkout over a host without that diff.
3. tf1, code: apply this branch's `analysis/` once the diff is understood,
   keeping the `mem_limit` edit. Rebuild with
   `GIT_SHA=$(git rev-parse --short HEAD) docker compose up -d --build enrich`.
   The four passes should still log `cycle N done`.
4. tf1, cleanup: neither the `coordination` nor the `leads` profile is running
   and no `leads_state` volume exists (checked 2026-10-10), so there is nothing
   to remove there. The three variables in `.env` are now unread and can go.
5. pi0, diff before sync. The collector builds from `~/kenya-monitor-2027`, not
   from the clone, and that tree is not a git checkout. Diff `collector/`
   against this branch and read it.
6. pi0, code: apply, rebuild. Delete `CLUSTER_PROMOTION_ENABLED` from `.env`
   (it is set today; the code no longer reads it). Leave `V2_PROMOTION_ENABLED`
   unset: turning v2 promotion on is the cloud-daily decision, not this
   branch's.
7. pi0, confirm in the log: no `cluster promotion disabled` or
   `cluster targeting` lines, `dynamic target` lines still present, and
   `monitor adapt --dry-run` runs.

## Open

- `deep_timelines._score_targets` reads the latest `kind=scores` with no age
  guard (so does `monitor deep-timelines --dry-run`): a run left over from a
  manual pass is used however old it is. The matching guard on the promotion
  side is `V2_PROMOTION_MAX_AGE_HOURS` (72h). Not added here: the age that is
  normal for `kind=scores` cannot be measured until the cloud daily writes it,
  and a guard now would flip deep timelines onto its suspicion fallback
  (1,444s to materialise on pi0) at deploy. Decide after the first week of
  daily runs.
- `kma.stories`, `kma.dashboard` and `modal_adjudicate.py` (without `--sample`)
  read persisted v1 output and will keep reading the last run indefinitely. The
  dashboard profile is not running on tf1 today.
